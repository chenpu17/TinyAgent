## 2. 语料与装置的攻防史（v1 → v1.3，每次泄漏都由实测攻击暴露）

1. **v1**：dev↔holdout 模板帧不相交 + 新噪声型 + e1 偏难移位。首跑即破：
   **glm 主动验证 id 前缀（`h-bug-0007` 式）与 dev label 的 100% 相关，直接
   `label = id.split('-')[1]` 拿满**——规则变难时模型会找元数据捷径。
   修复 = id 不透明（shuffle 后连续号）。
2. **v1.1**：id 修复后 e0 基线 0.49（≈朴素探针水位），但 e0p 一跑用**自写
   正则拿 1.0**——帧不相交只杀逐字迁移，共享基座槽位把类指示锚词
   （退款/验证码/报错/投诉……）近乎无损迁移。修复 = 锚词稀释 35% + 冲突 10%。
3. **v1.2**：deepseek@8192 一跑 1.0——解剖终判器发现它**只查标题表**：每类
   4 个固定标题帧 = 标签预言机，正文难度全部作废（冲突票还被类标题剧透）。
   修复 = 稀释/冲突票标题一律中性、标准票 60/40 → 标题预言机覆盖 1.0→0.33。
4. **v1.3 形状**：强手写关键词规则 macro F1 ≈ 0.68；标题预言机 0.33；
   逐字重叠 0；id 不透明。规则层覆盖上限落位——但残差句池仍是固定小集合
   （~44 句），外层可逐句语义判掉（枚举面，§5 基线 0.94 的成因）。
5. **v1.4 残差组合化**：稀释帧 6 → 12/类 + 全帧中性槽位（时间/次数/区位/
   等待/月份，零类信息），冲突帧参数化——残差唯一句 44 → 174+。验证：
   deepseek 探针的中间产物（288 行逐条 review 表）只剩 209/288 = 0.726，
   肉眼可见稀释帧语义误判（"共享日历到这一步就卡死" bug 判 howto）——
   枚举死、残差真需泛化判断。手写规则 0.70（不变，组合化针对枚举面）。

另两个装置发现：deepseek 会用**频次分析挖出固定噪声池并精确剥离**（合法）；
run_code 沙箱被真实使用（writeVerified 落 predictions + 自校验断言）。

**读数（级联档位的首个实测回答）**：

1. **弱类 account 不是内层模型盲区，是语料侧的语义边界**：glm 内层的
   account recall 0.765 / 0.784 ≈ ds 内层的 0.765——换内层模型修不了
   （主批发现 4 的"级联档位是设计里的对应机制"被证伪）。account 稀释帧
   （"按了没反应"型）的标注边界本身就需要人话标准澄清；级联档位的
   价值面不在此处。
2. **glm 作内层可用但显著更慢**：判别任务上 glm 没有外层那种烧穿问题
   （146–211 调用完成两跑；批量判别策略下 max_tokens=2560 思考密度可控），
   但墙钟 1633–3193s vs ds 内层 1105s 中位；单条判别策略（r2）直接撞
   5400s runner timeout。质量反而低于 ds 内层（0.89–0.90 vs 0.94–0.96）
   ——内层档位结论是 **ds > glm**（质量与墙钟双赢）。
3. **二阶路由方差跨内层模型复现**：r0 批量判别（146 调用）vs r2 单条判别
   （721 调用）——与 ds 内层的 116 vs 835 同款，策略选择仍是外层自由发挥。
4. **首个自发库采用事件（r2）**：该跑自发 saveLib 了判别库
   `lib/clf_llm.js`（clfSys/clfPrompt/clfParse + selfTest，正是技能教的
   判别库形态）、include() 52 次、先跑 dev 分片验证（preds_dev.jsonl
   对照金标）再判 holdout 分片——**v0.7.4 修订登记的 substrate 对齐场景
   （llm 判别循环里 include 判别库）在 e2 臂自发出现**。但采用是随机事件
   （r0/r1 未建库），且它出现在一个超时失败的跑里——采用 ≠ 收益。
   e1 的"零采用"结论应精化为：**零采用发生在"外层从零选执行路线"场景，
   判别库形态在 llm 臂有自发采用实例（1/3）**。
5. r2 的 timeout 是按实测行为记录（策略太慢 × runner 包络），不重跑；

## 7. 四路线外部对照（2026-09-23，产品放行当日收口）

§8.1 预登记的唯一保留验证项。同语料（v1.5 holdout 288）、同任务口径
（TASK_TEXT 原文含 v2.2 边界句）、同质量门槛（`v0b_eval.score` 单一计分源）。
装置与调优资源预登记于 `scripts/v0b_four_routes.py` docstring；输出档统一
32K（产品拍板——4096/8192 档思考税实测烧穿，见 pitfalls）。

| 路线 | 模型 | F1 | 交付 | 已知 tokens | 请求数 | 墙钟 |
|---|---|---|---|---|---|---|
| r1 外层直判 | glm-5.3-flash | 0.1648 | 26/288 ❌ | 74K | 1 | ~6min |
| r2 强模型分组 | glm-5.3 | **0.9743** | 288/288 ✅ | **95K** | 13 | 240s |
| r3 脚本+逐条 | deepseek-flash | 0.7767 | 288/288 ✅ | 619K | 288 | 621s |
| r4 TinyAgent e2 | flash 外层 + ds 内层 | 0.9411 | 288/288 ✅ | 1.10M | 330+ | 1895s |

（r1 首跑即 32K 档：`output_tokens` 精确 = 32768、只吐 26 行——烧穿指纹。
r4 的 1.10M = 外层 156K in + 227K out + 内层 310 调用 711K；另有 cache 读
1.47M 未计入，供应商计价下为低成本项。r1 交付不完整，其"单位成功成本"
不定义——按 §8.1 报零成功 + 总消耗 74K。）

**裁决：「run_code 降低总成本」在规则明确的批量分类任务上判负。**
单位成功成本 r2 = 95K / 1 次完整交付，是 r4（1.10M）的 **1/11.5**，质量还高
3.3 个点（0.9743 vs 0.9411）。这与合并批「最便宜的是基线」的方向一致且更尖锐。

**归因（四因素，装置内可分辨的部分）**：

1. **调用粒度**：r4 内层 310 次（≈逐条）× 每次重付思考段+上下文 ≈ 2.3K/条；
   r2 13 次组调摊薄 ≈ 330/条——成本差的大头是粒度不是编排本身。agent 本次
   自发选了细粒度（技能中的批量形态未用足）。
2. **模型档位混杂**：r2 裁判是 glm-5.3（强档），r4 外层 flash + 内层 ds——
   3.3 个点的质量差含档位因素，本对照未隔离「编排价值」。
3. **任务形态**：封闭词表 + 规则可一段话写清 = 分批调用的主场；agent 的
   增值面（探查/跨系统/多步/恢复）无发挥空间，全程纯开销。
4. **交付保证只算成本不算收益**：r4 的增量落盘/校验换 288/288 完整交付；
   4096 档下 r3 曾丢 23 条——可靠性在这套计分里不可见。

**产品结论**：TinyAgent 不应在这个任务族上卖成本；其立足点在规则不清、
需探查、多系统、需审计留痕的流程。若要隔离档位因素可补 r4 强模型外层
消融（~1M tokens，未跑，待产品定）；换任务族的四路线属新一轮预登记。
