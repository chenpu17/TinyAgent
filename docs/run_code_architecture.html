RUN CODE · 进程内 WASM 沙箱

别让模型当搬运工。
让它写代码，把活干完。

传统 agent 里，模型每碰一次文件都要走一轮对话：读一页、想一轮、再读一页—— 中间数据全部挤进上下文，成本和延迟随数据量线性爆炸。 run_code 反过来做：模型写一段 JS，在进程内 wasm 沙箱里 自主编排既有工具，数据在沙箱里流转，只有结论回到对话。

纯同步 · 无 tokio 纯 Rust 宿主 · musl 可静态 体积代价 +3.6 MiB 默认关闭 · 显式开启
01 · 为什么做

没有 run_code 时，问题出在哪

agent 的所有能力都经「对话」这一根管子进出。处理小文件没问题， 一旦碰上成批数据，这根管子就成了瓶颈——三个结构性痛点：

⇅

每一字节都要过模型上下文

读文件的结果必须作为 tool_result 回到对话，模型才能看到。900 行的文件 = 900 行进上下文，哪怕模型只需要其中一个总数。

⟳

轮次 = 成本 = 延迟

每次翻页都是一次完整的 LLM 往返。数据越大，轮次越多，token 账单和墙钟时间同步膨胀——还挤占 max_turns 预算。

▦

上下文被中间数据挤爆

中间结果不是结论，却霸占着最贵的资源：上下文窗口。窗口满了触发压缩，早期信息被摘要掉，任务质量随之劣化。

实现目的：把「数据处理」从对话里搬进进程内沙箱——模型负责决策与编排（写代码）， 沙箱负责搬运与计算（执行代码），对话里只流动意图与结论。
02 · 以前 vs 现在

同一个任务，两条路径

真实 A/B 实证：「读入一批整数（含超 2^53 的大数），算精确总和并写回结果文件」—— 模型在旧路径上手动翻页 17 次仍烧穿 300k token 预算，换 run_code 后一段 JS 一次完成。

以前：逐页搬运

read_file 翻页 → 模型看 → 再翻页 → … 每一页都进上下文
第 1 轮 · 读第 1 页
第 2 轮 · 读第 2 页
第 3 轮 · …
⋮ 共 17 轮，上下文里塞满逐页膨胀的原始数据
  • 17 次 LLM 往返，预算烧穿，任务没跑完
  • 中间数据全部留在上下文，触发压缩、丢早期信息
  • 大数求和靠心算/文本拼接，精度听天由命
VS

现在：一段代码

一次 run_code：沙箱内整读 → BigInt 求和 → 校验式写回
1 次调用 · 数据不出沙箱
  • 1 次工具调用完成全部搬运与计算
  • 上下文里只有代码与结论，干净且可压缩
  • BigInt 全程精确：4,629,700,416,936,914,141（float64 会静默错成 …913,920）
  • 写回经 host 回读校验，不谎报成功
17 → 1LLM 往返轮次
（同一任务实测）
300k+ → 一次token 预算
从烧穿到绰绰有余
0 字节中间数据进入
对话上下文的体积
03 · 技术方案

怎么做：JS 引擎编译成 wasm，嵌进二进制

不引入外部运行时、不引入 C 依赖、不引入 tokio——把 QuickJS-ng 编译成 wasm 直接嵌进 单二进制，由 wasmtime 36 以纯同步方式驱动。guest 从构造上就没有网络和文件系统， 想碰任何东西只能调宿主的既有工具。

LLM —— 决策层

发出 run_code 工具调用（载荷是一段 JS）。用法指南放进内置 skill run-code，模型需要时自取，不常驻上下文。

↓tool_use { code }

宿主（纯 Rust）—— 闸门与装配层

wasmtime 36 同步驱动；先过与外层同款的 hooks 闸门，再装配受限环境。

hooks 闸门每次工具调用可拒/可改参，双哈希分记原始与实发
四重限额fuel 指令 / 墙钟 epoch / 线性内存 / 调用次数
磁盘编译缓存wasm 机器码落盘复用，冷编译 ~10s 只付一次
两层开关cargo feature × 运行期 code.enabled，默认全关
↓受限运行环境（嵌入式 quickjs.wasm）

GUEST 沙箱 —— 执行层（能力构造性收敛）

不是「拦住危险操作」，而是根本没有那些能力：无网络、无文件系统直访。一切出访都是回环调用宿主工具，过同一套闸门与审计。

⟳ tools.call("read_file", …)
回宿主既有工具执行（文件 / shell / MCP），JSON 往返，每次计数
⟳ tools.budget()
随时查剩余燃料 / 墙钟 / 调用数 / token 配额
prelude 三件套（清单封闭）
readAll 整读 / readLines 行窗 / writeVerified 校验式写回
guest 输出预算 2M
与模型展示预算解耦——整读大文件的数据落 JS 堆，不进对话
04 · 执行流程

一次 run_code 调用，agent 在做什么

从模型发出代码到结论回到对话，共 6 步；每一步都有明确的检查点和账本。

1

模型发代码

tool_use: run_code，载荷是整段 JS——意图先被完整记录。

2

宿主过闸门

hooks 可拒绝/改参；原始输入记 in_hash，实发记 in_hash_eff。

3

装配沙箱

wasm 模块（缓存命中免编译）+ 四重限额 + prelude 三件套单行注入。

4

沙箱内执行

tools.call 回环读数据、BigInt 精确计算；console.log 实时透出为事件。

5

校验式写回

writeVerified：host 写盘后回读比对，不一致即报错，不谎报成功。

6

结论回对话

结构化 JSON 作 tool_result 进入下一轮；usage 折账、审计落盘。

失败同样诚实：超时 / 燃料烧尽 / 栈溢出 / hooks 拒绝 / 参数非法——一律封装成结构化错误 {kind, tool, retryable}，作为普通 tool_result 回给模型。模型看得懂原因，可以改代码重试； 沙箱已烧的 token 照常入账，不藏账。
05 · 得到什么

技术优势，逐条兑现

成本断崖式下降

中间数据不进上下文：轮次 17→1，token 消耗从「烧穿 300k」到「一次调用绰绰有余」。上下文窗口只装意图与结论。

安全是构造性的，不是补丁式的

guest 无网络、无文件系统——不是运行期拦截，而是能力根本不存在。想做事只能过宿主闸门，每一次都可拒、可改、可审计。

结果精确可信

BigInt 纪律消灭 float64 静默失真；writeVerified 回读校验消灭「写了半截说成功」；失败返回结构化错误而非含糊文本。

工程零负担

wasm 资产嵌进单二进制，无外部运行时、无 C 依赖、无 tokio；musl 静态构建照常，体积代价 3.6 MiB；默认关闭，开启才付成本。

全程可审计

代码原文、结构化结果、双哈希（模型要什么 vs 实际跑什么）、console 日志、token 账单——全量落 result.json，可回放、可归因。

行为有边界

fuel / 墙钟 / 内存 / 调用数四重限额兜底，guest 还能用 tools.budget() 自查余量主动收敛——死循环与失控在构造上不可能。
