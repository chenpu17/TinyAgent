## 1. 指挥目标与结论边界

**本轮要决定：基础 run_code 在哪些任务上值得继续投入，以及自然路由能否捕获收益。**
先发现最便宜可发现的问题，再用新样本检查修正是否成立；不以五场景全绿为目标。

三个决策分别记账：

1. **装置可用吗**：权限、计分、账目是否真实反映运行。装置不成立，先停止付费运行。
2. **值得追加验证吗**：有无质量不退化的成本/时间信号，或在相同资源边界内的可完成性差异。
3. **值得产品投入吗**：新实例上的结果、现实替代路线、需求频率与维护成本是否共同支持投入。

G1 只回答前两项；G2 仍是方向确认。小样本不认证可靠性，不宣称结构性不可替代，不改变默认开关。
两臂都完成时可以提出限定任务的成本假设；一臂失败时只报预算内完成情况，不借此宣布普遍降本。

### 1.1 需求证据与历史证据

- 产品负责人在 G0 写一页需求卡：具体任务、现行做法、运行频率、权限限制来源、允许的替代路线、人工时间。
- 没有客户材料也可进行 G1 工程探索，必须标 `synthetic / demand_unverified`；无需求证据不进入客户价值宣称或广泛发布决策。
- [四路线负结果](code_v0b_report.md) §7 保留，不重跑分类任务来翻案。
- [已有路由矩阵](run_code_routing_matrix.md)含 204 次历史运行。它比较契约/注入，不是当前 code on/off 因果对照；只用于选失败类型、约束假设，不与新结果合并计算效果。
- 超窗处理、字节保真、include 采用等历史证据保持原口径。`include 收益未证`不写成`能力不存在`。

## 2. 本轮只建一个小装置，三个任务

两个本地任务加一个两源分页任务，统一输出小型 JSONL；不先造三套服务器、恢复框架和大语料。
实例为确定性业务规则任务，不调用内层模型，不加入隐含标注口径。数据量是开发上限，不是收益阈值。

| ID | 任务与初始规模 | 数据/部署条件 | 要发现的问题 |
|---|---|---|---|
| T0 | 一个不超过 2 KB、12 条记录的文件；按明确谓词给出目标 ID 清单 | 两臂都有 shell 和文件工具；一次读取足够 | 额外描述、加载技能或不必要代码是否增加小任务成本 |
| T1 | 128 条订阅 + 256 条事件，总文件量不超过 60 KB；关联并输出符合条件的用户及事件数 | 两臂都有 shell，数据全在 workdir；Python/awk 路线合法 | shell 可解决时，开放 code 是否带来误用或额外开销 |
| T2 | 80 条订阅 + 160 条事件；两源各按 20 条分页，正常全量读取 4+8 页，总响应正文不超过 40 KB | **两臂都无 shell**；相同分页 MCP 工具；文件工具限定 workdir | 双侧原则上均可完成的分页关联，是否出现编排收益或实现/路由失败 |

共同业务规则的开发默认值：找出付费且有效订阅的用户中，至少出现一次 `confirmed=true` 且 `severity>=2` 事件的用户，输出 `user_id` 和满足条件的事件数。T0 以平面记录表达同一类明确筛选；任务文本直接写清规则。

实施约束：

- T2 用一个 `stdio` mock MCP 进程承载两个逻辑数据源，复用 `examples/mcp_echo.py` 协议骨架。首轮不验证多连接生命周期；有收益后才扩到真实多服务边界。
- 工具正常披露入参、分页契约与返回字段。不同源可用不同 join 字段名，但不刻意藏 schema、不用猜谜制造优势。
- 固定快照、稳定排序、正常游标、无随机故障；第一轮不同时引入分页错误、权限挑战和业务写入。
- 初始实例应有非空、非全集目标，保留谓词边界样例。独立验收器检查完整集合及计数，不要求特定实现语言或固定输出顺序。
- 允许直接工具批量调用；不强迫 B 一次一调用，不强迫 A 写代码。T1 走 shell 成功是合法结果。
- T2 的结论仅限该无 shell、分页-only 权限配置。若需求卡允许导出、服务端过滤或受控 MCP 脚本桥，进入产品比较前必须加入相应真实替代路线。
- G1 期间不把 T2 放大至超窗以促成优势。小规模没有优势是结果，不是装置故障。

### 2.1 数据、答案与环境

所有样本先在宿主生成不可变快照。模型只获得任务允许的数据；gold 与判卷逻辑不进入任务包。
T0/T1 的 gold 在产物封存后由外部判卷进程根据快照计算，避免 shell 看见现成答案文件。
T2 的服务端原始数据与生成器位于 workdir 外，文件工具启用实际路径限制；验证读取外部路径会失败。
不把“切换 cwd”或“stdio”当作 OS 隔离。若后续增加有 shell 的 MCP 条件，必须另验原始数据与凭证可达性。

G2 实例由另一评审者封存，在候选冻结前不得查看其输出或用于调提示词。若由同一人兼任，先封存生成参数与哈希，冻结前不运行候选。
换 seed 只是新数据实例；必须同时安排字段映射、页内排序、命中率或边界组合变化，且如实声明仍属同一任务族。

## 3. 两臂、共同权限、一个模型

| 条件 | A：自然选择、code 可用 | B：code 不可用 |
|---|---|---|
| 二进制 | 同一个 code-feature 二进制 | 同 A，不另编无 code 二进制 |
| code | `enabled=true` | `enabled=false` |
| 三原语 | `include=false`、`call_batch=false`、`llm.enabled=false` | 同样全关 |
| T0/T1 工具 | shell + read_file/write_file/edit_file/list_dir | 完全相同 |
| T2 工具 | 两个分页 MCP 工具 + 相同文件工具，无 shell | 完全相同 |
| 路径与宿主权限 | 文件工具限制 workdir；T0/T1 的 shell 仍按其实际 OS 权限审计，不能称完全沙箱 | 完全相同 |
| 模型 | 项目现用默认模型；开跑前冻结精确标识、供应商/网关及采样参数 | 完全相同 |
| 提示词 | 公共任务/交付纪律 + 现行 code 能力说明，on_demand skill | 同一公共任务/交付纪律，无不存在的 code 使用要求 |
| 状态 | 独立 workdir、全新会话、相同初始任务状态 | 同 A |

**主干预定义为“提供现行 run_code 工具包”的实际净增量**，包含必要工具描述与 skill 的成本，不谎称只隔离 wasm 执行器。
两臂公共提示词逐字相同；增量落盘、最终检查等通用策略均放公共部分。冻结完整差分，不能 A 用完整 code prompt、B 用残缺策略。
不把 `read_skill(run-code)` 强塞给 B；A 不加“必须使用 run_code”的任务指令，不使用 eager 注入。

实际注册工具、模型可见工具、guest 可调用工具分别导出为 manifest；自动工具与 skill 不能仅靠配置白名单推测。
先运行只读差分检查，除能力披露及 code 可用性外的意外差异一律阻止 G1。
不要求语义互斥的全文提示词机械相同，也不把差异藏在任务文本中。

## 4. 阶段、额度与放行规则

**任务实例、agent run、模型请求是三个不同计数。** 一次 agent run 可能包含多次模型请求；诊断与重试不免费。

| 阶段 | 工作量 | 单跑原生 token 闸 | 计划 token 包络 | 阶段末唯一决定 |
|---|---|---|---|---|
| G0 装置 | 离线验收 + mock provider 联通；0 次付费模型调用 | 不适用 | 0 | 可否开始六次首跑 |
| G1 首跑 | T0/T1/T2 各 1 实例 × A/B 各 1 次 = **6 runs** | 80,000 | 0.48M | 继续小规模诊断、停止，或进入 G2 |
| G1 诊断储备 | **最多 4 runs**；只查一个主要原因，最多一次候选修订 | 80,000 | 0.32M | 封存候选或停止；不用满也算完成 |
| G2 新样本 | 3 类 × 2 个新实例 × 2 臂 × 1 次 = **12 runs** | 80,000 | 0.96M | 限定保留、缩范围、停止，或提出一个 G3 分支 |
| G3 单分支 | 新登记，最多 **8 runs**，不得同时开恢复/语义/规模三线 | 120,000 | 0.96M | 是否值得另立项；不是自动下一批 |

这些数值是**研发资源分配上限与筛查规则，不是统计功效计算或商业收益门槛**。
首轮目标是尽早结束于 6 runs；G2/G3 的额度登记不代表要求执行或自动授权扩量。
G1 含全部诊断最多 0.8M，连同 G2 的计划包络最多 1.76M；仍有信号才讨论 G3。
本轮刻意不套用旧 `code_llm_design.md` §8.2 的每期三重复：那是语义/库正式初探协议；这里是独立登记的基础编排排错阶段，不能借其名义输出正式可靠性结论。

### 4.1 防止“软闸”冒充硬预算

- `max_total_tokens` 的原生闸有轮边界语义，最后一轮可能超额；80K/run、0.8M/G1 是调度与预计包络，**不是供应商扣费硬上限**。
- runner 在每次启动前检查已知用量、未知用量预留和剩余额度；不足以预留一个 80K run 时不启动。已超阈值立即停止启动后续 run，报告实际超额。
- 默认单请求 `max_tokens=32768`，沿用项目已知输出档以免把截断误判成能力失败；每 run 最多 20 turns、10 分钟墙钟。所有臂相同。原生 provider 重试配置也冻结并计费，runner 不自动重启整次失败运行。
- G0 记录上下文上限与最坏在途请求包络；若供应商/网关支持硬费用限额，直接使用现有设施。若没有，不为本轮新造代理：注明最大可能超额与缺失保障。
- 运行前必须填实际账单币种、冻结价表及本阶段费用停止值。默认从上述 token 包络按**最贵适用 token 单价保守换算**，缓存不当免费；团队已有更低费用限额时取较低者。不填价表不开付费运行。
- 费用字段、输入 token 是否包含缓存、reasoning 是否包含在输出内，在 G0 用供应商格式样例核对；总量只能计一次。未知费用预留，不能当 0。

### 4.2 G0 放行表

必须全部满足；不以额外付费模型运行代替离线排错：

1. 独立确定性参考程序能经许可入口解出三题；T2 通过 MCP 入口，记录正常页数和可达性，不从服务器原始数据直读来冒充可解证明。
2. 交付验收器能正确拒绝第 5 节的坏产物；无输出/超时也生成失败记录。
3. mock provider 完成 A/B 联通与事件采集，证明 code 开关、文件落盘、工具差分及 usage 解析实际生效。
4. 故意令一次 mock 失败/缺 usage，确认不会被聚合器删掉或按零成本计入。
5. HEAD、文件哈希、任务/工具/提示词、模型、运行顺序、价表和预算封存；所有必填字段有值。
6. 报告所有已知环境阻塞。mock 联通受限时先处理环境，不转为真模型“试试看”。

G0 不要求新造完整 hooks driver。复用现有 `tests/run_code_skill.rs` 与源码中的 hooks/gate 定向测试作为回归证据；无实时写操作的 G1 不提前承担 S4 全量工程。
若关键已知机制测试失败，区分产品缺陷与环境阻塞，修复后才开跑。
G0 先给两个人日的工程时间盒，用于暴露装置工作量，不作为两天必交承诺。到点仍未满足放行表就提交剩余项、阻塞与已用工时，不靠增加付费运行证明进度，不先扩成通用平台。

### 4.3 G1：六次自然运行后的分流

运行顺序固定为 `T0-B,A → T1-A,B → T2-B,A`；每个 run 使用独立状态，避免全 A 后全 B。
逐 run 立即封存；读完六次才决定是否消费诊断储备。发生泄漏、记账失败等装置错误时可提前停。

| 观察 | 决定 | 可用诊断额度 |
|---|---|---|
| 装置错误、答案可达、计费缺口 | 停止付费，修装置；原记录保留为 invalid，成本仍进研发账 | 修后最多重跑受影响的一对；消耗储备 |
| T2 两臂都成功，A 费用低至少 20%，墙钟不慢超过 20% | 仅标“值得新样本确认” | 可直接提交 G2，无须用满储备 |
| T2 A 成功、B 失败，且两侧配方有效 | 标“预算内完成性信号” | 复跑同一对一次，最多 2 runs；不宣称成本倍数 |
| A 未有效承接，但轨迹提出了可检验的 missed-route 假设 | 先人工检查代码参考路线是否有合理收益空间 | 最多 2 次强制 code 诊断；不计入自然臂效果 |
| A 代码错误/冗长策略主导成本 | 先离线回放定位；只允许一个有明确原因的候选修订 | 新候选 T2 配对 2 runs + 一个负例配对 2 runs |
| 两臂成功且接近、或 A 更差，没有具体可修原因 | 停止此任务族的扩量；保留可选能力 | 不为了“找到赢家”放大数据/换模型 |

额外约束：

- “有效承接”由 MCP 服务端事件与产物证明：run_code 实际读取/处理了任务数据；一次空调用不算。采用仅作解释指标。
- 强制诊断改变提示词，只回答“是否值得提出候选路由修订”。不得拿它与旧自然 B 作正式因果胜负。
- 路由文字一旦改动，候选须重新冻结；旧候选与新候选数据分栏。不得自动修改已关档的共享提示词/skill；通过实验配置显式门控候选。
- 有稳定交付失败，不能靠较低费用获得晋级；T0/T1 的误用/质量问题优先修正。
- 80K/20 turns/10 分钟边界导致的失败保留。只有预先冻结的参考可解性检查被证实错误才属装置问题；不能看到 B 失败才给 B/A 换 cap。
- 第四次诊断结束仍不清楚，输出“在本轮额度内证据不足”；不自动追加第五次。

### 4.4 G2：用新实例检查信号是否消失

触发：G0 合格、G1 存在具体可检验信号、候选已冻结、阶段回报说明下一批会改变什么决定。
仍使用同一模型、相同三类任务和部署条件。每类新增 2 实例；每实例只做一次 A/B 配对，第一实例 AB、第二实例 BA，具体顺序在开跑前封存。
不得在 G2 中途调 prompt/schema/阈值；若必须修，当前版本全部留档，本轮不以新旧混合值给结论。

**方向确认规则（研发取舍，不冒充显著性）**：

- 经济性方向：T2 的 2 对全部完成，两个独立实例分别算 `cost_A/cost_B`，均 ≤0.8；各实例墙钟比 ≤1.2。
- 负例约束：T0/T1 共 4 对中，A 不出现 B 成功而 A 失败；各任务类累计费用比 ≤1.2。超线意味着缩窄启用范围或停止当前候选，不以 T2 省钱冲抵负例失败。
- 可完成性方向：A 在两个 T2 实例均完成，B 在这两个实例均未完成；只支持这个资源边界下继续调查，不报告成本比胜利。
- 一次运行都无成功的臂成本比不定义。若成功率不同，先报成功率与全部消耗；单位成功成本为辅助描述，不替代配对质量判断。
- 其他结果记“未达到本轮追加投资门槛”或“证据不足”。不等于永久证明无效，也不自动触发更大样本。

每个任务实例列完整点值与差值。每类两实例、两对的结果不用于可靠性认证、普遍默认开启或跨领域外推。
20% 为此次控制研发投入选择的门槛；未来商业门槛须由需求卡决定，不能事后声称 20% 来自历史效应量。

## 5. 验收、成本与失败分类

### 5.1 新建严格验收器，旧评分与历史结果不动

新任务不直接沿用 `scripts/v0b_eval.py:score/aggregate` 的接受条件。
旧函数会合并重复 ID、跳过坏 JSON，旧聚合还会排除 partial；历史读数冻结，新装置单独版本化。

最小离线用例：完整正确；缺行；重复 ID；未知 ID；错误计数；非法 JSON；合法 JSON 但类型/schema 错误；空产物；空 gold 与非空误报；运行失败但已有完整产物。

主成功标记 `delivered_exact`：允许的时间/预算窗口内，交付文件严格合法，目标 ID 集合与计数完全一致，产物可独立读取。
结束原因单独登记：若产物已完整而模型后续触闸，仍记完成交付，同时报告非正常结束与所有浪费；不得为任一臂偷偷使用不同成功定义。
进程外超时的产物在终止并封存后评分；截止后的补写不接收。排序与无关空白不计业务错误。
F1、缺失/误纳入数用于诊断，不能替代机械任务的 exact 交付门。

### 5.2 成本主口径

- 主费用 = 全部模型尝试的真实计费项目之和，包含缓存、失败与供应商重试；外部工具费用有则单列加入。模型未知用量给区间/缺口，不填 0。
- 另报墙钟、请求数、外层工具数、MCP 实际调用数、code 次数/错误数、输入/输出/缓存分项；不把外层调用减少当作费用下降。
- `cost_per_success = all_attempt_cost / delivered_exact_count`，零成功为 null。每个任务/部署分别计算，不混合 T0/T1/T2 得出普遍胜率。
- G1 不比较“自发采用跑”和“未采用跑”来估计因果收益；主分析始终按分配的 A/B 条件。
- 调试人工时间、装置开发时间、付费失败、无效装置运行和强制诊断进入研发总账，不能藏在实验主表外。
- 若采用费用区间，仅在 A 上界/B 下界仍达到门槛时说费用信号成立；区间跨阈值则成本不可判。

### 5.3 四类状态，不互相改名

| 状态 | 例子 | 处理 |
|---|---|---|
| product_failure | 算错、漏页、代码报错、合法预算内未交付 | 保留为失败；不修装置来抹掉 |
| apparatus_invalid | gold 泄漏、错发工具、判卷错误、状态未重置 | 保留原始证据和费用，暂停后修；新 run_id，不覆盖 |
| infrastructure_failure | 网络断开、供应商服务不可用 | 保留全分配运行视图及分层说明；最多在储备内补完整配对，不选择性补败臂 |
| insufficient_evidence | 无效运行耗尽额度、费用不确定、点值混合 | 停止并说明缺什么；没有自动扩量权 |

成本聚合仍包含所有已发生的付费尝试。效应表标明哪些配对无效及为什么；“全分配运行视图”与有效装置视图并列，不让异常删除改变主叙事。

## 6. 最小工程交付，不重造评测平台

新增文件为**团队待实施接口**，本文创建时尚不存在；命名可小改，但责任与产物不可省：

| 文件/产物 | 职责 | 不做什么 |
|---|---|---|
| `scripts/code_value_eval.py` | 读 manifest，A/B 启动、状态隔离、预算检查、封存、汇总；默认 dry-run，付费必须显式 `--execute` | 不改 `v0b_eval.py` 的历史配方、不自动扫全部阶段 |
| `scripts/code_value_fixture.py` | 三类确定性小任务、独立 gold、一个双源 stdio MCP mock | 不建 5–10 MB 语料、不建多服务器运维 |
| `scripts/code_value_score.py` | 严格验收与全部费用统计、机器可读结果 | 不从模型自报“验证通过”推断成功 |
| `scripts/tests/test_code_value_eval.py` | 第 5 节反例、失败计费、版本差分和 run 数上限测试 | 不重跑所有历史 benchmark |
| `artifacts/code_value/<batch_id>/` | manifest、每 run 证据、总账和机器可读配对表；现有目录不覆盖 | 不提交密钥、完整私人环境变量或模型 key |
| `docs/code_value_reports/<batch_id>.md` | 一页主报告 + 原始工件索引、阶段裁决 | 不把不同版本的最好结果拼接 |

G0 先验证评分与账目，再实现启动环节。优先复用现有事件、usage 和 MCP 协议；没有必要为三题先建数据库、web 看板或全新的编排框架。
工程拆成小提交，每份提交写清验证命令。涉及共享源码/提示词的候选修复另列，不能混入“修评测脚本”提交。

### 6.1 manifest 必填

`batch_id / stage / experiment_version / code_head / dirty_diff_hash / binary_hash / fixture_hash / task_hash / prompt_hashes / prompt_diff / tool_inventory / feature_flags / model / gateway_identity / sampling / price_snapshot / cost_currency / cost_stop / token_stop / turn_limit / wall_limit / retry_policy / run_schedule / success_rule / gate_rule / demand_status`。

gateway_identity 只保存不含凭证的标识。fixture/tool/schema 改动也改版本。每个 run 保存：

- `run_id, instance_id, arm, repetition, order, config_redacted.json`；
- `events.ndjson, result.json, stderr.log, server_events.ndjson`（无 MCP 时可无）；
- 原始产物、`validation.json, usage.json, summary.json`；
- 时间、结束原因、actual route、expected vs actual 工具、完整性及费用缺口。

### 6.2 团队职责与边界

- **评测负责人**：维护假设、版本、预算与阶段决定；只放行可改变决策的下一批，不按“跑满次数”验收。
- **开发负责人**：实现当前工单及离线测试；定位失败，不自行改评分、扩大语料或提高 cap。
- **独立复核人**：检查公平性与原始轨迹，至少复核一对全部请求/账目，并复核所有失败。可由现有团队成员兼任，但不能只看汇总表。
- **产品负责人**：补需求卡、真实替代方案及商业门槛。缺证据不阻挡 G1 工程排错，但限制产品宣称。

每阶段结束默认停在回报点，负责人按已写规则给出下一份工单；不需要每个 shell 命令向用户重复询问。
原始预算内的 G0 与 G1 准备按本方案推进；G2/G3 只有阶段回报与明确派工后开始，不由 runner 自行解锁。

## 7. 后续只允许选择一个扩展方向

G2 后根据未决产品问题选一项，重新冻结小配方；本节不授权现在开发：

| 条件 | 下一项 | 最小设计边界 |
|---|---|---|
| 新实例方向一致，但生成波动仍决定是否投入 | 有界复现 | 选 1 个正向实例与 1 个负例，各追加 2 次 A/B 配对，共 8 runs；只确认当前候选，不同时扩任务族 |
| 分页编排有信号，真实客户需要跨系统写入/审计 | 端到端工作流 | 在现有两源任务上加计划→同策略审批→幂等写回→独立核对；两臂同 hooks；对合法替代工作流计入接入与人工成本 |
| 只有受限部署存在收益 | 第二部署条件 | 若真实需要 shell，补 shell on 的 A/B 配对与合法数据访问路线；不能拿无 shell B 比有 shell A |

| 语义迭代仍是明确投资项 | 语义路线 | 运行真实 r2 driver；若要隔离编排，给双方同等模型调用权限。分配质量/费用前沿，不继承 +0.03/2× 阈值 |

基础 run_code 通过不等于 include/callBatch/llm 通过。每个原语只在对应问题需要时单独消融，不一次打开全部开关。
无 shell 的 mock 胜利未获需求支持时，合理动作是保持可选能力、停止市场外推；不是自动投入更大的 mock。
