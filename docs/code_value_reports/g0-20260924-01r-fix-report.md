## 一、计费与停止行为（P1-01）

**修复前反例**（复核复现）：result.json 缺失的 run 被记成
`requests_happened=false`、cost=0——烧了钱但账面为零；一个 run 部分请求
没报 usage 时，已知费用被整体吞掉，停止线只看「已知费用」→ 六跑全部启动。

**修复后结果**：
- 完整性三态：`usage_complete` / `partial_unknown` / `usage_missing`；
  已知费用下界（`cost_known_lower`）与完整性**分开**——部分未知时
  `cost=null` 但下界保留。
- result 缺失或**损坏**（半截 JSON，修复前直接 json.load 崩溃）→ 从
  events.ndjson 核账（turn/usage 事件差 + usage 帧 token 累计），绝不归零。
- 未报账请求按 65,536 tok/请求预留、整轮缺按 112,768 tok 预留，折算成
  货币风险进停止判断：**已知下界 + 未知预留 ≥ cost_stop 即停**。
- 首轮保守策略：任一 run 用量无法核账 → 立即停止启动后续 run，证据封存。
- 主指标 `cost_per_success`：任一 run 费用未知即 null，下界单列
  `cost_known_lower_total`——不拿混合口径当主指标。
- `validate_price_snapshot`：五项齐全、单价有限非负、币种非空且与
  `cost_currency` 一致；负价/NaN/零停止值全部拒绝。
- `cost_stop` 在 ledger 里显式标注为「run 间停止线；非供应商扣费硬上限」；
  在途超额风险上界（`inflight_overrun_risk_tokens`）含输入+输出+重试。

**回归入口/工件**：
- `test_run_g1_partial_unknown_stops_subsequent_runs`（真实入口：首跑
  partial_unknown → 只跑 1 run、stop_reason=usage_incomplete、下界 0.0011
  保留、后续 run 无 started.json）
- `test_run_g1_cost_stop_triggers_on_lower_plus_reserve`（missing → 预留
  112,768 tok 折算 0.1128 ≥ 0.05 → cost_stop 触发）
- `test_run_g1_missing_result_accounted_from_events` / 
  `test_run_g1_corrupt_result_accounted_from_events`（events 核账 1100 tok，
  不归零不崩溃）
- `test_run_g1_normal_runs_all_six`（对照：全正常 → 六跑、主指标有值）
- `test_require_paid_prereqs_rejects_invalid_numbers`（负价/NaN/零停止值）
- 封存批次 `artifacts/code_value/g0-20260924-01r-fix/`：failure run 检出
  partial_unknown（unreported=1、reserve=65536）、missing-usage run
  reserve=112768、ledger 4 run 无剔除、cost_per_success=null。

**剩余边界**：
- 预留口径（65,536/112,768）是保守估计不是实测——真实 G1 跑完可校准。
- cost_stop 是 run 间停止线：单 run 在途消耗仍可达
  `inflight_overrun_risk_tokens`（已在 ledger 显式单列，非硬上限）。
- events 本身若被进程外因素截断（如磁盘满），核账下界也只到截断点——
  这是证据链的物理边界。

## 二、冻结配方的执行校验（P1-02）

**修复前反例**（复核复现）：manifest 记录过哈希 ≠ 执行时校验——冻结后
手改 configs/（换模型）或二进制重编译，run-g1 照跑；价表可以手改 manifest
填入，无显式冻结步骤。

**修复后结果**：
- `verify_frozen_recipe`：任何模型请求前重算并逐项比对——二进制哈希、
  fixture 快照哈希、任务文本哈希、prompt 配方、逐 run 配置内容哈希
  （`config_hashes`）与配置模型、工具清单合法（inventory problems==[]）、
  六跑顺序。漂移即拒绝执行（不进入 run 循环，零 run 启动）。
- 价表补全 = 显式 `finalize-g1` 子命令：校验价表 → `freeze_final` 写
  config_hashes + final_frozen_at → 之后 run-g1 才可能通过。**手改
  manifest 填价表在 `require_paid_prereqs` 即被拒**（final_freeze_missing）。
- 不比对 HEAD / 工作树状态——无关文档提交不使批次失效。

**回归入口/工件**：
- `test_run_g1_refuses_recipe_drift`（binary_hash_drift / config_model_drift
  → SystemExit，零 run 启动）
- `test_run_g1_refuses_hand_edited_price`（手改价表 → 付费前置缺失）
- `test_finalize_g1_explicit_freeze`（finalize 后手改配置 → config_drift 拒）
- `test_require_paid_prereqs_blocks_without_price`（合法价表但无冻结痕迹
  → 拒）

**剩余边界**：
- 校验面是「冻结配方」的完整性，不是供应链完整性——二进制本身被
  同哈希替换（哈希碰撞）不在防御范围。
- prompt 配方哈希覆盖 `prompt_parts()` 的输出；若未来 prompt 来源加新
  依赖（如环境变量），需同步进 recipe。

## 三、中断与重复启动（P1-03）

**修复前反例**（复核复现）：进程中断的 run（有 events/answer 无 summary）
重新执行 run-g1 时被静默覆盖——费用证据丢失；两个执行者同时跑同一批次
无互斥。

**修复后结果**：
- `claim_run_slot`：启动前 O_EXCL 原子创建 started.json（pid+时间）；
  目录里已有**任一**证据文件（started/events/result/summary）即拒绝覆盖，
  报「拒绝覆盖……新尝试用新 run_id」。中断记录原样保留。
- `mark_run_completed`：completed.json 独立于 started（summary 落盘后写）。
- 并发双执行者：第二个在 O_EXCL（或证据检查）处失败——互斥不靠锁文件
  约定，靠原子系统调用。
- 异常退出（进程死在半路）也留下可问责状态：started.json 已在、
  events 按现状封存、score_run 照常记账（usage_missing + 预留）。

**回归入口/工件**：
- `test_run_g1_refuses_interrupted_run`（中断 run 重跑 → 拒绝 + 原证据
  未破坏）
- `test_run_g1_started_marker_atomic`（O_EXCL 并发互斥）
- `test_run_g1_crash_midway_preserves_evidence`（半路死 → usage_missing
  记账 + 停后续 + 重跑被拒）
- 封存批次 runs/*/started.json + completed.json 全套在档。

**剩余边界**：
- started.json 的 O_EXCL 互斥在同一文件系统内原子；跨文件系统（NFS 等）
  语义弱化——本装置单机运行，不构成实际边界。
- 「新尝试用新 run_id」目前是人工约定（报错信息引导）；批次级「自动
  续跑未完成 run」不在本工单范围。

## 四、答案隔离（P1-04）

**修复前反例**（复核复现）：gen_stats.json 的 gold_digest 含明文答案 id
（t1/t2 的 user_ids 列表），评测 shell 直接可读；restrict_to_workdir 与
「删 gold.json、挪目录」都不是隔离证明。

**修复后结果**：
- **摘要不可逆化**：gold_digest 只留 `{count, gold_sha256}`（规范化答案
  的 sha256），明文 id 全部移除；判卷进程从快照现算 gold 并对哈希对账
  （对不上即 RuntimeError，防快照被篡改后静默判错）。
- **历史泄漏面排查**（工单要求 survey）：
  - 历史批次 wd/answer.jsonl、scenario.json（mock 场景明文）→ 在
    `artifacts/code_value/` 下 → Seatbelt deny；
  - **git 历史**：`GOLD_T0` 字面量（scripts/tests）与 fixture 生成器
    （含 solve_*）已进提交——`.git` 加入 deny 面，`git show` 读不出；
  - 同批次兄弟 run 的 wd/answer.jsonl（gold 明文）→ 逐 run deny；
  - v0b_artifacts_v1.4 / v0b_routes：旧一代语料，与当前 fixture 无
    gold 重叠（已核对），不在答案面。
- **真实 shell 入口实测**（不是配置写了就算）：`verify_seatbelt` 启动前
  用真实 sandbox-exec 双向探针——答案面读不出内容 + workdir 可写；
  封存批次四 run 探针全绿。额外实测：用 t1-B 的 profile 试读兄弟 run
  answer.jsonl、fixture digest、`git show HEAD:scripts/tests`——全部
  读不出。
- 修复过程中发现并修掉一个真 bug：deny 清单原用 `run_dir.parent.name`
  取批次名，实际是 `runs`——当前批次把自己 deny 了（g0 首跑全红的根因）。
- 隔离不可用（非 macOS / 无 sandbox-exec / 探针不过）→ **阻塞回报**，
  不静默降级、不跑带答案泄漏的盲测。

**回归入口/工件**：
- `test_run_g1_refuses_interrupted_run` 等真实入口测试在 seatbelt 桩下
  跑（隔离本身另有真实探针门）；
- 封存批次 `runs/*/seatbelt_check.json`（真实探针结果）+
  `runs/*/seatbelt.sb`（实际生效的 profile）；
- g0 六项门第 3/4 项含 seatbelt_isolation 检查（探针不过即 FAIL）。

**剩余边界**：
- Seatbelt 是本机（macOS）机制；Linux 上 `seatbelt_profile` 返回 None →
  按工单语义阻塞（需要 Linux 等价物才可在 Linux 开付费跑——G1 在本机
  macOS 执行，不构成当前阻塞）。
- deny 面是枚举式（fixture/历史批次/兄弟 run/源码/文档/.git/凭证）；
  若未来答案新增存放点，须同步进 `seatbelt_profile`。
- 探针覆盖 `file-read*`；Seatbelt 本身的逃逸（如内核漏洞）不在装置
  防御范围。
