## 工单 01：G0 装置先行，禁止付费模型调用

**目标**：证明测得准、记得全、两臂公平，准备三题六跑；不在本工单证明特性有价值。

按以下顺序交付：

1. 记录 HEAD、工作树、二进制及历史 E0–E3/r2 配方指纹；不修改历史配方。
2. 实现版本化严格验收器，覆盖方案 §5.1 的全部坏产物；费用账包含失败、缓存与未知用量。
3. 准备 T0/T1/T2 三个小实例：12 条单文件、128+256 条本地关联、80+160 条双源分页。先用许可入口上的确定性参考程序解出，封存数据/任务/schema。
4. A/B 只改变现行 code 可用包；三原语全关，同模型，同公共提示词。T0/T1 两侧都有 shell，T2 两侧都没有。
5. 实现默认 dry-run 的最小 runner、独立状态、不可覆盖的 run_id、六跑固定顺序及最多四跑储备；不存在总是跑完 G2 的默认参数。
6. 用 mock provider 检查一次正常交付、一次失败和一次缺 usage；验证失败有记录、未知消耗不变成零、产物缺失不被跳过。
7. 冻结 manifest，包括真实注册工具、提示词差分、模型标识、实际价表、币种、费用停止值、软 token 闸及在途超额边界。
8. 复核人核对一对完整轨迹/账目、所有异常及权限；提交 G0 一页报告，停在交接点。

**约束**：不调共享提示词，不加 inner llm/include/callBatch，不构建恢复 runner，不放大数据，不跑模型档位矩阵，不访问真实业务写 API。若发现产品 bug，单列定位证据与最小修复，不伪装成评测配方更新。

**验收**：方案 §4.2 六项均有命令/工件证据；`paid_model_requests=0`。装置或环境不合格就报告阻塞，不用真实模型绕开。
工程时间盒先设两个人日；未完成就回报剩余项和工时，不要求仓促放行，也不自行扩成通用评测平台。

可复用的当前源码：

- `examples/mcp_echo.py`：stdio MCP；`examples/mock_openai.py`：provider mock，二者用途不同。
- `scripts/v0b_eval.py`：启动与结果字段参考；不得继承旧 score 的宽松接受或 aggregate 的 partial 排除。
- `tests/run_code_skill.rs` 与 `src/tools/run_code.rs`：分页/副作用/hook 定向测试。
- `docs/run_code_routing_matrix.md`：历史失败类型，不能当本轮开关对照数据。

- 每 run 原生 token 闸 80K、单请求输出上限 32768、20 turns、10 分钟；同配置同模型。
- 六跑计划 0.48M token；原生轮边界可能超额，按 manifest 同时报真实消耗与在途风险。

## 工单 03：诊断储备（可不执行）

全 G1 总计不超过 10 runs，储备最多 4 runs。不要把不同诊断各做四次。

派工必须写：观察 → 单一原因假设 → 将改哪个变量 → 哪个结果推翻假设 → 具体 run_id 配方 → 费用余额。

仅可从以下动作选一个主方向：原配方完整配对复跑；强制 code 的独立诊断；一个候选修订后 T2 配对加一个负例配对。修装置后的重跑也占储备。
强制诊断与旧自然结果分栏；候选改动后重新冻结，保留原记录。第四次追加后结束，不追加“最后再确认一次”。

## 工单 04：G2 新样本确认（另行派发）

必须附 G1 信号、候选指纹与“本批会改变哪个决定”。
三类各两个新实例、每实例一次 A/B 配对，共 12 runs，计划包络 0.96M token；按方案 §4.4 裁决，不在中途调参。
结果只支持继续/缩范围/停止的研发决定，不能凭 12 runs 宣布普遍可靠或默认开启。G1 含诊断加 G2 的计划包络最多 1.76M。

```text
结果：逐任务 A/B 交付、费用、墙钟；不写“总胜场”：
装置 / 产品 / 基础设施问题及各自证据：
本轮是否改过配方；旧版本数据位置：
客户需求证据状态与允许外推范围：
复核人 / 复核工件 / 未验证范围：
建议：停止 / 修一个问题 / 进入下一阶段（三选一）：

```

任何人不能以“结果差异不够明显”为由自行增量、换模型或调金标。可以提前停止并提交负结果；停止是合格交付。
不需要每项日常实现向用户请求确认，但扩大预算、改变假设或启用下一阶段需要评测负责人的明确新工单。
