# 产物落盘健壮性——设计选型稿（P3，一页）

日期：2026-09-23。状态：**待选型**（动手前过产品确认）。

## 问题（一句话）

模型在长任务里会"算完不落盘"：e2-r0 在内层把 575/576 判完，却死在外层
max_tokens 上、`predictions.jsonl` 一行没写——评测记 0.0（假 0），真实能力
F1 0.9020。同型死亡已三次（v1.2 ds@4096 死在格式化轮、v1.4 写完 288 行
review 表后死在逐条复核轮、e2-r0 死在写文件前的最后一轮）。

死亡形态共性：**工作内容只在对话流/沙箱内存里，磁盘产物是最后一格**；
cap 烧穿在"复核/格式化/再想一轮"上。现有缓解都不覆盖：
- 协议 v2.2 的「无复核句」只压住了模型自觉的复核轮，管不住"算完就散"；
- `salvage_on_max_tokens` 只救**无 tool_use** 的纯文本截断轮，且 nudge 文案
  只说"给个简洁结论"，没提落盘。

## 三案

### 案 A：教学层——"先落盘"纪律句（skill + 协议文案）

在 run-code 技能正文与 agentic-code 协议里加一条正面纪律：
**「产物分块增量写：每完成一段就 writeVerified 落盘一次；写完产物后任何
进一步打磨都是亏的」**。

- 成本：0 核内代码；文案即规格——run_code 工具描述/skill 正文三处同源
  （`docs/finetune_support_design.md` 附录 A 有依赖），改字走修订记录。
- 证据：协议级句已证明有效（Q5 边界句把 account recall 0.765→0.931）；
  "先落盘"的**正面**纪律从未单独测过，按 mini 纪律 1 跑 @288 即可判定。
- 风险：prompt 层对"不做某事"（不复核）有效，对"持续做某事"（边算边写）
  遵循率未知——这正是要 1 跑测的。

### 案 B：核内——salvage 扩面到"零产物截断"

`salvage_on_max_tokens` 加一个触发面：max_tokens 截断且**本 run 无任何
成功写盘记录**（write_file/writeVerified 的写事件台账）时，wrap-up nudge
换用落盘变体：「先把你已得出的结果写到磁盘，再收尾」。

- 成本：核内小改（agent.rs salvage 判据 + nudge 常量 + `agent_tests.rs`
  配套 loop 测试，mock provider 不连网）。
- 限制：**救不全**——截断轮若带 tool_use 仍按现契约不 salvage（e2-r0 的
  死亡轮形态未核实是否带 tool_use）；salvage 轮本身还要再烧一段 token，
  且"落盘变体"是产品文案向评测场景靠近了一步（现契约刻意不耦合任何
  评测的答案格式——"写到磁盘"是通用工程指令，可接受，但要明说）。
- 判据实现：run 级已有 records 台账可判"有无成功 write"，不需要新管道。

### 案 C：评测装置——假 0 防护（不是产品修复）

`v0b_eval.py` score() 前探测「stop_reason=max_tokens 且产物缺失/行数不足」
→ summary 标 `partial: true` 而非记 0.0，聚合时单列。

- 成本：runner 脚本几行；0 核内改动。
- 价值：纯装置卫生，防假 0 再污染臂间对照；对产品行为无影响。

## 建议

**A + C 组合，B 暂缓**：A 是唯一针对死亡根因（不写）的产品级修复且成本
近零；C 是必须的装置卫生（B/A 任何验证跑都会再产生假 0 风险）；B 等获得
A 的 mini 读数后再决定——若教学层遵循率高，B 的复杂判据不值得；若低，
B 也只救一种死亡形态，届时优先考虑的可能是"截断轮带 tool_use 也给一次
落盘机会"这个更激进的契约改动（另行预登记）。
