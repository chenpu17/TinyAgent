## 1. 为什么要重做，以及 v0.1 的错在哪

四路线外部对照（`code_v0b_report.md` §7）裁决：规则明确的批量分类任务上「run_code
降低总成本」判负（r2 强档分组 95K vs r4 1.10M，11.5×，质量还高 3.3 点）。归因四条，
**v0.1 声称"修掉三条"，实际只修了一条**：

| 归因 | v0.1 的说法 | 复核结论 |
|---|---|---|
| 调用粒度 | 场景 1 强制同构调用 | **保留**（唯一真正可设计的一条） |
| 模型档位混杂 | 纪律「同档位」 | **已修，但范畴要说清**：把两侧拉到同档只回答「固定档位下编排有无增量」，**不能回答「run_code 降低总成本」**——r2 用强档赢是合法客户选择，不是缺陷 |
| 任务形态利于基线 | 剥掉书面标准 | **未修到点上**：r2 从未见过 TASK_TEXT 的规则段（它自己从 dev 归纳标准，`v0b_four_routes.py:137-141`），所以"剥掉书面标准"没碰 r2 的真实机制（分组摊薄 + 强档 + 4 路并发）；封闭词表这个"分批主场"原样保留 |
| 交付保证不可见 | 场景 3 把可靠性进判据 | **是口径范围，不是装置缺陷**：四路线里 r2/r3/r4 都交付 288/288，交付在那一轮不区分臂；把 S1/S3/S4/S5 整场景移出成本比较，等于承认成本仍输 |

v0.1 的三个硬伤（三份评审独立命中，已逐条核实）：

1. **对照臂是被假设行为截肢的稻草人**：`v0b_eval.py:156` 给所有臂的白名单含 `shell`，
   而 `run_code_requirements.md:490-492` 项目自己早写明「**本套件无 shell 臂**——任务
   全部可用 awk 一条管道解决，**带上 shell 的对照会几乎全场最便宜**；code 的不可替代
   场景是**无 shell / 锁死部署**与工具返回的分页数据」。v0.1 的 S1/S5 把带 shell 的
   基线称作"真对手"，与项目自己的既判直接冲突。
2. **S3 测的是提示词差异**：`Persist artifacts incrementally` 只存在于
   `examples/prompts/agentic-code.md:40`（非 code 版 `agentic.md` 没有），run_code 跨调用
   零状态（`agentic-code.md:111`）——增量落盘是教学层纪律（`artifact_robustness_design.md`
   案 A），不是 run_code 机制。
3. **S5 三分之二子轴已证**：大数据 0→1 与大批量数值精确运算在 §10 三批 + GAIA 锚点
   已证；未证的只有"字节保真原语补齐后从未对照验证"这一个窄点。

## 2. 已证 / 未证边界（本次场景的排除线与登记簿）

**已证，不再测**：

- 数据装不进对话 → code 质变（§10 三批 + GAIA 唯一结构性分叉 + P2 large regime
  code 19/20 vs trad 5/20）。
- **数据能在一两页 `read_file` 内读完且心算可靠 → 直接读更省**（§8 P2 校准后的判据；
  注意不是"≤400 行"——P2 small regime 300–800 行 code 反而省 5 倍，尺寸律是题型依赖的）。
- 封闭词表批量分类 → 强模型分组更便宜（四路线裁决）。
- 代码资产跨会话复用（include）→ 收益未证（E1 cold 零建库 0/6 + warm 零采用 0/3；
  E2w 采用成立 2/2 但质量低于 e2、方差收窄判负）。
- **AppWorld 两题探针（登记为第五条，v0.1 漏登）**：多 API 编排 + MCP 分页 + schema
  探查的同族任务上，awlikesong 总 token −23.4% 但 awclean 非缓存输入 +137%（v2 优化后
  墙钟 276s vs 145s 中位、非缓存输入 38,620 vs 16,927）。单题单次、方向混合、作者自己
  声明不构成结论——**它是 S1 唯一的同族先行读数，S1 的假设必须专指超窗量级才能区分**。

**已关档不再投入**：A③ 提示词层、Tier-2 索引 skill、规模再放大。

## 3. 五个价值场景

> 每条场景**必须显式声明两侧工具白名单**（v0.2 新增的硬纪律，见 §4.1）——这是
> v0.1 最大的漏洞，也是本稿所有判据的成立条件。

| # | 场景 | 未证轴 | 白名单构型 | 臂 × 重复 | 包络 |
|---|---|---|---|---|---|
| S1 | 多源探查与跨源关联 | 分页数据 niche（超窗） | 双 regime | 3 臂 × 3 | 3–5M |
| S2 | 无书面标准下的迭代收敛 | agent 增量的**均值** | 现状默认（含 shell） | 2 臂 × 2 档 × 3 | 2–4M |
| S3 | 断点续做的成本 | 恢复粒度（**成本差**） | 现状默认 | 2 臂 × 3 中断点 | 0.6–1.2M |
| S4 | 审批与审计的 per-call 归因 | hooks 归因面 | 现状默认 | 3 臂 × 3 | 0.6–1.2M |
| S5 | **路由方差：该用代码时是否用** | 采用率（收益的期望值） | 现状默认 + 超窗族 | 1 臂 × 5 | 1–2M |

合计 **7.2–13.4M**（账：臂 × 重复 × 单跑包络；单跑包络取自 e2 四臂主批实测
116–835 内层调用 / 17–114 万 token 的形态，S2 上限按最重跑取）。

### S1 多源探查与跨源关联

**问题**：数据超窗**且** join 键要先探查才知道时，代码承接是否仍不可替代？§10 只证了
单源大数据；本场景测项目自宣布的两个 niche 中的「工具返回的分页数据」。

**装置**：3 个 stdio mock MCP server（零依赖 Python，骨架抄 `examples/mcp_echo.py`；
`examples/mock_openai.py` 是 LLM provider 侧 HTTP SSE mock，**不是** MCP 体例）。
工单 / 用户订阅 / 事件日志，各自分页（limit ≤ 50 + 游标），字段名刻意不对齐
（`uid` / `user_id` / `account`），需三步 join 得到「受影响的付费用户清单」。
全量 5–10 MB。任务文本不含 schema 说明。

**装置不变量（必须成立，否则 shell 臂可绕过 MCP 直读数据源）**：数据源不在 workdir
内、凭证只存在宿主内存、server 只经 stdio 暴露；shell 继承父进程环境
（`src/tools/shell.rs:62-70`）这条通道必须走不通。此不变量写进预登记并附验证脚本。

**臂（白名单显式）**：

| 臂 | 模型 | 工具 | 说明 |
|---|---|---|---|
| A（被测） | 同档 | 默认白名单（含 shell）+ `code.enabled` | run_code 承接 |
| B2a | 同档 | 同 A 的**全部**工具，仅关 `code.enabled` | **shell 在册的对照**——项目既判里"几乎全场最便宜"的构型 |
| B2b | 同档 | 默认白名单**去掉 shell** + 关 `code.enabled` | 锁死部署 regime 的对照（逐次工具调用） |
| B1（可选） | 强档 | 无工具，评测侧导出 2% 样本文件 | r2 形态（归纳标准 + 24 条分组）；数据不进上下文，结构性失败 |

**预登记判据**（**合取**，任一不满足即判负）：

1. 质量：清单对 gold 的 F1 ≥ B2a 且 ≥ B2b（平手即算不劣，质量差值单列报告）；
2. 成本：单位成功成本 ≤ min(B2a, B2b) 的 1/2（口径见 §4.4）；
3. **成功地板**：清单 F1 ≥ 0.9 才算"成功交付"，否则该臂单位成功成本**不定义**；
4. **DNF 处置**（预写）：任一臂零成功交付 → 该臂成本不定义，按四路线 r1 惯例报
   零成功 + 总消耗，成本判据转"结构性 / 证据不足"，胜负只由判据 1/3 定。

**诚实预期**：分两 regime 报，**结论分别限定**。B2a 若胜出，S1 只证明"锁死部署 niche
成立"，不证明 run_code 优于 shell 脚本路线。反向先例必须引：AppWorld 同族任务在小数据
量上方向混合（§2 第五条），S1 的假设专指超窗量级。

### S2 无书面标准下的迭代收敛

**问题**：E2 只证了**一致性**（3 跑 F1 极差 0.012、gates-off 臂 0↔0.97 翻硬币），
**均值增量从未证**。这是"agent 增量"主张的正脸，也是本稿唯一的成本面场景。

**装置**：

- **任务文本**：新增独立常量（**不改 `scripts/v0b_eval.py:53` 的 `TASK_TEXT`**——
  它是全臂共用的全局常量，就地改会破坏 E0–E3 冻结读数，且违反 `code_llm_design.md`
  §10.1「其余差异不得藏在临时提示词中」）。新常量 = 剥掉 v2.2 边界口径句
  （`v0b_eval.py:57-59`）的变体；改动按 §10.1 显式登记为"新臂的文案差异"。
- **语料**：复用 v1.5（dev 192 / holdout 288），**真值不动**——本场景只改任务文本，
  不改生成器语义。（v0.1 写的"4 条隐藏维度"是改生成器语义、属新语料，与"复用生成器"
  互斥，已删。）
- **计分**：继续 `from v0b_eval import score`（单一计分源）。

**臂**：

| 臂 | 提示词 | 说明 |
|---|---|---|
| A（被测） | 随二进制发货的 `agentic-code.md` + run-code skill | 自测 → 修订 → 重判 |
| B（基线） | **r2 配方原文**（`v0b_four_routes.py:137-155`：归纳 ≤40 行标准 + 每 24 条一组 + 4 路并发）作为策略提示，登记"谁写的提示词" | 上一轮赢家配方必须给到基线，否则装置公平塌陷 |

**档位与内层**（v0.1 漏定，这是成本面胜负的唯一开关）：主口径 = 外层两档都跑
（强档 `glm-5.3` / 默认档 `glm-5.3-flash`），**内层 = 外层同款**（消除"被测臂多一个
模型档位"的混杂）；级联档（内层 `deepseek-flash`）作附读数单独登记。

**预登记判据**（任一不满足即判负）：

1. 质量增量 ≥ **+0.03**（锚：合并批 Q5 边界口径句把 account recall 0.765→0.931，
   折 macro-F1 ≈ +0.02，即"一条弱类边界被澄清"的效应量）；
2. 单位成功成本 ≤ 基线 **2×**（锚：§7 强档 r2 95K vs r4 1.10M——超过 2× 意味着
   同预算直接买强档档位更划算）；
3. 方差同时不劣化（A 臂 3 跑极差 ≤ 0.02）；
4. **聚合口径预写**：DNF 计 0.0 进均值 + 完成跑中位**双口径并列**（基线历史方差是
   0↔0.97 翻硬币，只报一种口径即可翻转结论）；
5. **兜底**：样本不足 / 区间无法区分时结论为"证据不足"，不强行判胜（照 §8.2）。

### S3 断点续做的成本

**问题**：判负归因第 4 条「交付保证只算成本不算收益」从未被检验。但复核后**该轴的性质
变了**：两侧都靠**文件**做 checkpoint，`--resume` 把历史原样重放进上下文（README
§会话持久化），基线同样可以 resume——"重试即重复副作用"不是无 run_code 的结构性质。
**因此本场景预登记为成本差，不声称能力差。**

**装置**：mock 写 API（请求计数 + 可注入 503/断流）；任务 = 500 条记录**机械谓词**
筛选后写入（"判"必须是确定性规则，不引入语义判断，否则质量轴混入交付轴）。幂等键
契约写进任务文本。第 1 跑用 `max_total_tokens` 预算闸在中途停住（`stop_reason=
"budget_exceeded"`，exit 125，轮边界判定、session 已落盘），第 2 跑 `--resume` 续做。

**装置缺口（必须新写 runner，不能沿用 v0b_eval）**：`v0b_eval.py:106-125` 每 run
`rmtree` workdir 重铺，且用 `--session none`（:182）——而 `--resume` 与 `--session none`
互斥（`src/main.rs:318-325`）。新 runner 需保留 workdir + 真实 `--session <file>` +
可注入中断。

**臂**：两侧**同等恢复待遇**（都 `--resume` + 同 workdir + 同断点注入）；唯一差异 =
是否编入 run_code。

**预登记判据**：

1. 副作用重复 = 0 —— 作为**两臂各自的达标线**（非区分判据）；
2. **续跑 token 增量对比**为区分判据（run_code 臂外层历史短、重放便宜 vs 基线数百次
   工具调用的长历史重放贵）；
3. **降级条款（预写）**：若基线三条全过，该轴判为**成本差**，不声称能力差——正好落回
   §4.5 的逐判据分栏。

**重复**：≥3 个不同中断点（单跑过的硬线太脆，装置抖动即翻车）。

**诚实预期**：run_code 跨调用零状态（`agentic-code.md:111`），两侧同提示词（§4.3），
所以这测的是"恢复的成本"，不是"能不能恢复"。

### S4 审批与审计的 per-call 归因

**问题**：hooks 面从未对照验证。复核后**主张收窄**：判据里五分之四是通用 hooks 面，
只有 per-call 归因触及 code 特性（`ctx.subagent` 的 `__code__` 标签）。

**臂（三档，"裸 agent"不是真对手）**：

| 臂 | 说明 |
|---|---|
| A（被测） | `set_hooks` 注入两条策略：删除类操作无审批票据即 Deny、PII 字段必须改写 |
| B1 | **config / 提示词层收紧**——真实客户的最小成本方案：`fs_write_dirs` 白名单 + `tools` 去 shell + 策略写进系统提示词（`README.md:786` 明说 hooks 不是内置安全边界，宿主自己的策略层才是） |
| B2 | 裸 agent（无任何策略）——只作下限参照 |

**装置前提**：hooks 不在配置 JSON 里（`src/config.rs` 无 hooks 字段，已核实），须走
Python 绑定 `set_hooks`；**若要判据 2 的 run_code 来源标签，wheel 必须是
`maturin develop --features code` 构建的**（默认 wheel 只有 hooks）。`--resume` 重建的
agent 需重新 `set_hooks`。

**预登记判据**：

1. 越权实际执行次数 —— **三臂各报**（0 即无区分度，不写"预期 > 0"这类不可证伪的预测）；
2. per-call 归因（**唯一真差异**）：每次工具调用可归因到来源（`ToolCallRecord` 只有
   `name/input/output/is_error/meta`，无 subagent/origin 字段；`ctx.subagent` 是并行
   真并发下唯一可靠的来源标签）；
3. 拒绝理由以模型可见错误回到模型且被正确处理：不硬崩 + 同一被拒调用连续重试 ≤ N
   次（N 预登记）；
4. 成本可按 per-call 归集（`ToolCallRecord` / `meta.llm`）。

**降级条款（预写）**：若 B1 也 0 越权，本场景降级为"hooks 面可用性验收"，
**不声称不可替代性**。

### S5 路由方差：该用代码时是否用

**问题**（v0.2 新增，替代 v0.1 的字节保真场景）：特性的**收益期望 = 收益 × 采用率**，
而采用率从未被测量过——它只以零散轶事形式出现：E1 warm 零采用 0/3；产物健壮性 mini 跑
`routes` 里 run_code **0 次**（历史 e2 两跑均 run_code + 内层 ~1300 次调用）；r4 四路线
自发选细粒度；AppWorld 两题触发成功但成本分化。这是**唯一"最可能判负"且产品最需要**的
读数：若模型常常不用代码，前四个场景的收益都打折扣。

**装置**：复用 v1.5 holdout 288 + e2 配置 + 32K 输出档，**同一臂重复 5 跑**，只读：
`routes["run_code"]`、内层调用量级（`meta.llm.calls`）、stop_reason、单位成功成本。
另加一档"该用代码"的超窗任务族（§10 large regime 形状，1–9 MB）测**漏用率**。

**预登记判据**：

1. 采用率（run_code ≥ 1 次的跑占比）与内层调用量极差；
2. **漏用惩罚**：未采用的跑的单位成功成本 vs 采用的跑；
3. 若采用率 < 3/5，判定为"收益不可靠"——特性收益期望须按采用率打折陈述。

**诚实预期**：这是唯一可能判负的场景，且判负的代价最小（便宜、装置现成）。

### 附录 A：字节保真与数值精确——**机制验收**（不是价值场景）

v0.1 把它列为价值场景是名不副实：三个子轴里两个已证（§2），唯一未证的是
`copy_bytes` / `writeVerified` / raw 分页 / BigInt 纪律补齐后**从未在真实模型下验收**。
且 v0.1 的判据 2（BigInt）是 **substrate-relative 的伪判据**——float64 失真正是
QuickJS 沙箱自己的问题，Python 基线零成本通过。

**改为机制验收，无对照臂（省 token）**：

- 规模两档（50 KB / 5 MB）——判据 3 需要两档才能测"token 水位不随规模增长"；
- 判据：产物 sha256 逐字节一致；数值精确（**实现语言不限**，不写 BigInt）；
- 报告口径：确定性正确性验收，**不进成本面**，也不声称对基线的优势。

## 4. 贯穿纪律

### 4.1 工具白名单必须显式声明（v0.1 最大漏洞的止损条）

每条场景的每个臂，预登记时必须写明**完整工具白名单**。默认白名单是
`["shell","read_file","write_file","edit_file","list_dir"]`（`v0b_eval.py:156`）——
**"无 run_code"不等于"无 shell"**，两者能力差一个数量级。凡结论涉及"优于基线"，
必须同时报"shell 在册"与"无 shell"两个 regime，或把结论限定到 niche 并引用
`run_code_requirements.md:490-492` 作为既知前提。

### 4.2 同档位（含内层）

外层与被测臂同档；**内层模型必须显式规定**（被测臂能多调一个模型，基线不能——这是
上一轮"档位混杂"归因的延伸，v0.1 只覆盖了外层）。S2 的档位两档都跑。

### 4.3 同提示词

两侧给同一份系统提示词。`Persist artifacts incrementally` 只存在于 code 版提示词
（`agentic-code.md:40`），凡场景涉及落盘/恢复，两侧要么同源给、要么同源删。

### 4.4 单位成功成本口径预登记

- 分子 = **全部尝试总成本**（含失败与重试轮消耗），cache 读**单列不计入主口径**
  （四路线里 cache 读 1.47M，不是小项）；
- 分母 = **成功交付数**，成功须同时满足质量地板（§S1 判据 3）与交付完整性；
- 任一臂零成功 → 该臂该量**不定义**，报零成功 + 总消耗；
- 该量的计算收进与 `v0b_eval.score()` 同级的**单一计分源函数**，禁止各 driver 手工除法。

### 4.5 判据先冻结，且按判据分栏（不按场景）

- 体例照 `code_v0b_report.md` §5.6（判胜标准写于批完成前）；装置指纹（语料
  `gen_stats`、mock server 哈希、任务文本、白名单）随预登记登记；登记挂**预登记报告段**，
  建议同时纳入 `scripts/check_eval_apparatus.py`（现仅保 E0′ 一个装置）。
- **每条判据预登记时标注"能力/成本"**，报告按判据分栏。v0.1 按场景分栏是错的：
  S1 判据 2 与 S3 判据 3 本身就是成本判据。

### 4.6 烟雾门与账目

每场景先 1 跑 + 人工读产物三样（死法 / 路由形状 / 分数水位），红灯处置是修装置；
跑前算 token 账（§3 表已列臂 × 重复 × 包络）。

## 5. 执行顺序与前置

顺序：**S5**（最便宜、装置现成、且是唯一"最可能判负"的轴）→ **S2**（信息量最大，
决策相关）→ **S1**（最贵、装置最重）→ **S3**（需新 runner）→ **S4**（driver 不确定
性最高，见下）。

次序弹性：S4 的前置若超半天（绑定 driver 需新写、hooks 不在 config JSON、可能要
code-feature wheel），S2 提前、S4 顺延。

**待探明前置项**（未探明不得预登记对应场景）：

- **S1**：mock MCP 的数据源不可从 shell 到达这条不变量的验证脚本；`readOnlyHint`
  注解（决定 `callBatch` 白名单覆盖；注意 MCP 工具默认 `Sequential`，入批**无墙钟
  加速**，callBatch 的收益是省外层上下文重付）。
- **S3**：新两阶段 runner（保留 workdir + 真实 `--session <file>` + 中断注入）。
  `--resume` 语义已核实：只恢复消息历史 + 压缩归档，**不恢复**工具调用状态/预算/cancel/
  MCP 连接/hooks；悬挂的 `tool_use` 被补一条 `[interrupted — session recovered after a
  crash]` 的合成 `is_error` 结果，**绝不重放**（`src/session.rs:76-104`）。
- **S4**：绑定 driver 形态（须复用 `v0b_eval.score()` 单一计分源）；code-feature wheel
  构建前提。
- **S5**：超窗任务族的语料来源（复用 §10 large regime 生成器还是新造）。

## 6. 与既有装配的关系，以及本稿不测什么

- **不改** E0–E3 / E2w 的任何装置与读数；四路线结论不重开。新任务文本走独立常量，
  不动 `TASK_TEXT`。
- 新增装置若引入新的 LLM 可见文案（任务文本、mock 工具描述），按
  `code_llm_design.md` §10.3「评测门常备化」处理；任务文本的冻结/属主登记按 §10.1。
- **本稿不测**：跨会话 include（已判负）；"run_code 优于通用 agent"（S1/S5 的对照臂是
  构型受限的，结论只限 niche）；通用 agent 能力（S3/S4 有部分判据不区分臂，已标注）。
- 若 S1/S5 全胜，能得出的结论是"在无 shell / 锁死部署与 MCP 分页数据这两个 niche 上
  承接是结构性必要的"，**不能**得出"run_code 降低总成本"——唯一成本场景是 S2。
