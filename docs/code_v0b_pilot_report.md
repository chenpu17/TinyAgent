| 项 | 值 |
|---|---|
| 定位 | V0-B 的第一片试点，**不是正式 V0-B 轮**：单轮、无交错、无级联档位、合成语料 |
| 装置 | `scripts/v0b_native_pilot.py`（真二进制 `--release --features code`、真网关 `测试模型.md`） |

**本片回答的问题**：V0-A 的路线③④是 python 脚本模拟的；native 栈（agent loop +
run_code 沙箱 + include/llm/callBatch 门）在真实网关上第一次整体上场地，行为如何。
任务文本**方法中立**（只给目标不给路线）；路线是模型在各臂门控下的自主选择。

## 1.1 同路线四跑的散布（本片最重要的单一数字）

E0/E2/E3 三臂在方法中立任务下**全部自主选择 shell+python 规则路线**
（probe 为明示指令不计），同一路线族的四次运行质量散布：

| 运行 | 门 | 结局 | F1 |
|---|---|---|---|
| E0 | 全关 | 关键词规则 + 锅炉板剥离 + 末尾自校验，end_turn 干净收尾 | **1.000** |
| E2 | 开两层 | 规则写完 predictions 后摘要轮被截（max_tokens） | 0.862 |
| E3 | 全开 | 启发式迭代中两轮烧满 4096，predictions 未写 | **0.000**（有效率 0%） |

**门的开启与质量无正向关系**（全开的 E3 最差、全关的 E0 最好）——质量由
"探索路径是否恰好收敛到模板精确匹配 + 是否在预算内落盘"决定，即语料泄漏面
× 完成纪律的方差，不是能力增量。单轮 E 矩阵在此语料上不构成质量证据。

## 2. 机制验证（probe 臂，明示走 run_code+llm+callBatch）

M3 原语第一次过真实网关，全链无人工干预：

- **分层策略自然发生**：dev 金标标题/正文精确匹配规则覆盖 237/288（dev 内零冲突），
  剩余 51 条 bug/feature 边界项交 llm（labels 两词表 + prompt 同写词表要求）。
- **callBatch 真并发**跑 51 条 llm；**调用额度分批纪律生效**：三次 run_code 撞
  200 次额度上限（JS error: incomplete 241/288 等），guest 按 skill 教学落盘
  检查点（writeVerified）+ 下一轮续跑，最终 288/288。
- **max_tokens 自适应**：首试 128 对 reasoning 模型不够（16/51 有效），模型自己在
  下一轮提到 512——M0 报告预言的思考烧穿模式在 native 场景由模型自行处置。
- **LD-12 台账落盘**：240 内层调用、56,586 token 全部 known_usage、0 unknown
  （result.json 逐 run_code meta.llm 聚合，无预占悬挂）。
- **质量**：288/288 全对（F1=1.0）。**诚实归因**：合成语料 dev↔holdout 模板同源，
  精确匹配规则本身就是泄漏面（V0-A 已声明该局限；native 跑法把它显式暴露了——
  模型第一轮探查就发现了该结构）。1.0 不能外推到真实工单。

## 3. 关键发现

1. **路由缺口是第一发现**：E2/E3 门全开 + 内置技能披露（LLM 判别段在），
   glm-5.3-flash 在方法中立任务下**不选 llm 路线**——三次独立运行（E0/E2/E3）
   都走 shell+python 规则 + 外层自行判边界（E0 无 llm 可选属预期，E2/E3 是
   门开而不取）。披露存在不足以移动路由；这正是 E0′（三问边界句）臂
   要测的干预，优先级上调。
2. **外层开销主导 native 成本**：probe 墙钟 459s 中，内层 51 条判别本身很快，
   大头是外层 16 轮探查/写规则/调度（57.6k in + 35.9k out + 235.8k cache_r）。
   V0-A 模拟路线④没有外层循环成本，54s 是纯内层时间——**native 对照必须在
   同一二进制上跑（本片做法），不能拿模拟数字当 native 预期**。
3. **外层 max_tokens 截断不是 cap 问题是纪律问题**：E2 首跑 2048 截断后试点把
   cap 提到 4096（记录在案），E3 依然在 turn 8/turn 10 各烧满 4096——glm 的
   思考烧穿（V0-A 发现 #1）在外层会吃掉任何给定的 cap，提 cap 只是把截断
   推后并把成本翻倍。真正缺的是"先写产物再优化"的任务纪律（E0 有、E3 无），
   这是外层提示词/任务设计的干预点，不是配置调参能解决的。
4. **shell 是平行通道**：agent 用 shell heredoc python3 做了 run_code 能做的
   大部分事（规则归纳/统计）。矩阵按先例保留 shell（不用删工具逼迫选择），
   但这意味着 E 臂隔离的是"能力+披露"的增量，不是"唯一路径"——解读时牢记。
5. **E2 质量与 V0-A 基线①同级**（0.8623 vs 0.850–0.895），complaint 召回
   0.655 低于 C2 少数类 0.75 门槛——外层自行判边界在该类上并不稳。
6. **E3 未完成（完成纪律风险）**：同一路由下，E3 的探索更深——它自己发现了
   合成语料的 FILLERS 噪声模板并在启发式质量迭代中反复修规则，turn 8 与
   turn 10 各烧满 4096 输出（12773 个 thinking 增量），`max_tokens` 截断、
   salvage wrap-up 一次性额度也只换来一次 tool 调用即再截断，**predictions
   全程未写** → 有效率 0%，按装配文档 C2（≥98%）为硬失败。E2 同样终于
   截断但 predictions 已先落盘（10 轮里第 8 轮写完）。同路由两次运行一成
   一败——方法中立任务下 flash 档外层模型没有"先写后优化"的纪律，矩阵
   臂方差大，正式轮 ≥3 重复是必须而非锦上添花。
7. **触发文案 → 读取 → 不采纳的完整链**：E3 中 run_code 触发文案生效
   （模型 read_skill 了 run-code），但读完仍回 shell 启发式。披露的三个
   层级（工具在、技能读了、文案推）都不足以移动路由——干预必须在任务
   边界句层（E0′ 假设），这把 E0′ 从"文案对照"升格为路由研究的核心臂。

## 4. 对正式 V0-B 轮的建议（进装配文档修订）

1. **语料重生成升为阻塞项**：dev↔holdout 模板不相交（消除精确匹配/锅炉板
   剥离泄漏——本片 E0 就靠它拿满），并加"更严移位"（新模板池/新噪声型）。
   在此之前 E 矩阵的质量列只是方差测量（见 §1.1），能力增量不可读。
2. E0′ 臂（边界句变体）为**路由干预的主假设检验**——先跑 E0 vs E0′，
   确认三问边界句是否移动 glm 的路线选择，再谈 E2/E3 的能力增量。
3. 任务文本/外层提示加"先写中间产物再迭代"的完成纪律约束（E3 反例）；
   评估按 C2（有效率 ≥98%）把未完成臂记硬失败（本片 E3 即此类）。
4. 正式轮 ≥3 重复 + 交错（本片单轮，同路线散布 1.0/0.86/0.0）；probe 的
   明示指令臂保留为机制冒烟，不进质量结论。
5. 成本口径补 cache_read（网关前缀缓存对 native 外层循环影响显著：E0 173.6k、
   E2 73.7k、E3 114.7k、probe 235.8k cache_r——冷启动 req1_unc 勘误口径继续适用）。

## 5. 局限（必须随结论一起读）

单轮无重复；合成语料（模板同源，质量数字不可外推）；网关无货币计价
（token+墙钟口径）；无级联档位（单内层模型）；probe 是明示指令上界而非矩阵臂；
E2 首跑的外层 max_tokens 中途调整（2048→4096，装置层、记录在案）。
