TINYAGENT · RUN_CODE

run_code 什么时候会被触发？

绝大多数任务里它不会被触发。没有程序化触发器——触发与否是模型按任务形状做的判断， 规则全部写在它每次都能读到的工具描述与技能里。这张图整理「看得见之后」的完整决策面。

前置假设（本图不展开）：cargo feature 已编入 · code.enabled = true · 顶层 agent（task 子 agent 看不到 run_code）
01 · 谁在决定

没有触发器，只有模型的判断

代码里不存在任何「满足 X 就自动启用 run_code」的规则。每一轮对话， 模型都能看到 run_code 的工具描述，用不用它，是模型对每个任务做的逐任务决策。 系统能做的是把「什么该用、什么不该用」的判别标准写在模型必然读到的三个信号面里。

三个引导信号面

  • 工具描述（~889 字符）：随每次请求的工具 schema 下发——身份、环境、封闭的助手清单、返回纪律、「何时用/何时不用」的口诀都在这。
  • 内置技能简介：技能名 run-code + 一行描述常驻 system prompt，不占对话历史、压缩不掉。
  • 技能正文：深契约（read_file 三模式、字节保真复制、批量闭环模板、BigInt 纪律）不进 schema，模型写非平凡代码前被引导 read_skill 按需加载。

为什么这样设计

描述瘦身是因为工具 schema 每次请求都要付 token——把「什么时候用」的判断依据放进描述， 模型每一次做决策时都拿着同一份规则；细节则移到可压缩、可回收的技能正文。 描述、技能正文、设计文档附录 A 三处同源同步，改动必须三处一起动。

判别口诀（原文写死在描述里）：
「如果需要在自己回复里记住大量中间数据才能完成，就该用代码。」
02 · 决策树

多数任务走左边，少数任务走右边

左边是默认路径：能一步完成、能一条管道完成、数据量小——都不该惊动沙箱。 右边的共同特征是中间数据的规模或步骤的数量超出了对话上下文适合承载的范围。

模型收到一个任务（run_code 可见）
每一轮都重新判断一次：这个任务的最佳承载方式是什么？
不触发 ← 绝大多数任务
描述明确写「不要用本工具」的情形
单步可完成

单个工具调用就能做完

读/写一个文件、改一处代码、跑一条命令——直接调 read_file / edit_file / shell，更省更稳。

管道可完成

一条 shell 管道能做

排序、去重、求和、单遍过滤——shell 可用时优先 shell，不开沙箱。

小规模同构

十来个小文件的简单修改

直接多次工具调用反而更直观可控，沙箱的编排价值体现不出来。

无工具需求

问答 / 写作 / 分析类任务

纯生成型任务连工具都不一定需要，run_code 自然不会进入考虑。

触发 → 中间数据装不进对话
一次沙箱执行替代几十轮工具来回
循环 / 批量

几十~几百次同类调用

分页拉全再逐条删除/修改/点赞；几十个文件的批量校验、改写、重组。循环写在 JS 里，不再一轮一轮等模型发指令。

大文件加工

数据装不进对话上下文

readAll 整读后聚合/过滤/统计，只 return 摘要。实测对照：不用代码时模型退回 17 次手动翻页，把 run 级 token 预算烧穿在重读历史上。

多步 / 关联

跨文件 join、分组、JSON 嵌套处理

多步数据加工的中间结果留在 JS 堆里（受内存上限约束）不进对话；代码经 JSON 直传，免去 shell 转义烦恼。

批量闭环

先数数 → 批量执行 → 校验对账

「计划—执行—校验」闭环：目标去重、逐条记账、数量不齐显式报错。单次 200 次调用额度装不下时，按引导分批落盘续跑。

一句话总结：单步能完成就不用、一条管道能做就不用、要背大量中间数据就该用。 run_code 的价值不是替代既有工具，而是把「几十轮 read_file + shell 来回折腾」压缩成一次沙箱执行——省的是 token 和轮次。
03 · 触发之后

被调用 ≠ 一定跑完

模型一旦决定调用，还有一组运行期闸门。这些是终止与拦截，不是触发决策—— 但用户看到「调了却报错」时，原因都在这里。

⏱

入口门：启动前直接拒

取消标志已置位 / 墙钟已过 → 沙箱不启动，燃料消耗为 0。短任务在单个检查间隔内就能跑完，所以必须先过这道门。

✋

拦截层：单条调用被拒

hooks Deny、deny_paths 命中、写出工作目录、写穿符号链接——单条调用报错可 try/catch，不影响后续调用。

🧮

调用额度：默认 200 次/次

每次执行独立计满、不跨次累计；失败和写错名的调用也照扣。超限即终止本次执行，报错文案引导分批落盘续跑。

⏳

墙钟 / 燃料 / 内存 / 栈

timeout_secs（与父 run 剩余时间取紧）、fuel 确定性预算、mem_mb 线性内存、384 KiB wasm 栈——任一超限强制终止，已写盘文件保留。

🛑

取消：宿主可随时打断

Ctrl-C / Esc 置位取消标志，约 10ms 内在下一条 wasm 指令处停下；在飞的内部工具调用会跑完。终止原因如实归因。

📦

结果纪律：返回值必须紧凑

只 return 摘要（统计数字、路径、样例行）；大数据写文件后返回路径。返回值与 console 日志共享尺寸上限，超限截日志保返回值。

审计不缺位：无论正常返回还是被终止，每次执行的内部调用逐条进审计 trace （名称 / 成败 / 耗时 / 输入哈希），连同调用计数、fuel 消耗一起落进 result.json 的 meta——跑到哪一步停的，事后都查得到。
